scripts/matching_engine.py
──────────────────────────

Purpose: Core algorithmic engine for staffing recommendations

This is the intellectual property of the platform - the core IP

Key Components:

  1. MatchingEngine Class
     ├─ __init__: Load all data sources
     ├─ score_employee_for_opportunity: Calculate multi-dimensional score
     ├─ rank_candidates: Sort all employees for opportunity
     ├─ generate_explanation: Create transparency narrative
     └─ flag_risks: Identify concerns for decision-makers

  2. Scoring Functions (One per dimension)
     ├─ score_skill_match(employee, opportunity)
     ├─ score_seniority(employee, opportunity)
     ├─ score_sector_fit(employee, opportunity)
     ├─ score_availability(employee, opportunity)
     ├─ score_certification(employee, opportunity)
     ├─ score_career_alignment(employee, opportunity)
     └─ score_location_fit(employee, opportunity)

  3. Explanation Generator
     ├─ explain_scoring: Detailed breakdown
     ├─ explain_strengths: What makes candidate good fit
     ├─ explain_considerations: Concerns or risks
     └─ generate_recommendation_text: Summary statement

  4. Utility Functions
     ├─ calculate_skill_proficiency_score: Score from proficiency level
     ├─ time_until_available: Days until employee can start
     ├─ sector_match_strength: Quality of sector alignment
     └─ certification_status: Active vs. expired vs. missing

Example Usage:
  ```
  engine = MatchingEngine(data)
  recommendations = engine.rank_candidates(opportunity_id=2001)
  
  for rank, employee_rec in enumerate(recommendations[:5], 1):
      print(f"{rank}. {employee_rec['name']}")
      print(f"   Score: {employee_rec['overall_score']}")
      print(f"   Rationale: {employee_rec['explanation']}")
  ```

Design Decisions:
  ✓ Separate functions per scoring dimension (testable)
  ✓ All scores 0-100 (normalized, comparable)
  ✓ Weights configurable (business logic adjustable)
  ✓ No external ML libraries (explainable, lightweight)
  ✓ Comprehensive scoring rationale (transparent)

pages/recommendations.py
────────────────────────

Purpose: AI-assisted staffing recommendation interface

Workflow:

  STEP 1: OPPORTUNITY SELECTION
  ├─ Dropdown or search to select opportunity
  ├─ Displays opportunity details (skills, seniority, duration)
  └─ Shows "Find Candidates" button

  STEP 2: CANDIDATE RANKING
  ├─ Runs matching engine
  ├─ Displays top 10 candidates ranked by score
  ├─ Shows quick stats (name, seniority, score)
  └─ Expandable for details

  STEP 3: DETAILED REVIEW
  ├─ Click candidate to expand
  ├─ Show scoring breakdown (all 7 dimensions)
  ├─ Display explanation narrative
  ├─ Highlight strengths and considerations
  ├─ Flag any risks (red/yellow)
  └─ Compare to other candidates

  STEP 4: ALLOCATION
  ├─ "Allocate" button for selected candidate
  ├─ Updates availability status
  ├─ Confirms opportunity status change
  └─ Returns to selection for next opportunity

Additional Features:
  • Comparison mode (side-by-side candidate view)
  • Filter recommendations (seniority range, sector required, etc.)
  • Export recommendation details
  • Save recommendations to history
  • Feedback mechanism (rate recommendation quality later)

Design:
  • Large, clear scoring display (0-100 number prominent)
  • Color-coded scores (90-100: green, 70-89: yellow, <70: red)
  • Narrative explanations in plain English
  • Risk flags immediately visible
  • One-click allocation minimizes friction

4. WHY SEPARATE CSVs
================================================================================

ARCHITECTURAL DECISION: NORMALIZED DATA MODEL

Instead of one big CSV, we use normalized relational-style CSVs.

Advantages:
──────────

✓ DATA INTEGRITY
  • Foreign key relationships prevent orphaned records
  • No duplicate data (e.g., employee name repeated for each skill)
  • Updates in one place propagate everywhere
  • Easier to maintain consistency

✓ QUERY EFFICIENCY
  • Join employee with skills only when matching needed
  • Dashboard can aggregate available% without loading full history
  • Faster filtering and searching
  • Scales to 1000s of records easily

✓ FLEXIBILITY
  • Easy to add new skills or certifications without modifying master record
  • Can track many-to-many relationships (employee ↔ skills)
  • Simple to add new attributes without schema migration

✓ ANALYTICS
  • Can analyze skill distributions independently
  • Certification trends visible separate from employee records
  • Project complexity independent analysis
  • Composable for custom reports

✓ DATA QUALITY
  • Standardized skill names (no "Python" vs. "python" vs. "Py")
  • Certification status clearly tracked
  • Proficiency levels constrained to valid set
  • Easier to validate and clean

Alternative (Not Used): Single Big CSV
──────────────────────────────────────

employees.csv with columns:
  id, name, seniority, skill1_name, skill1_prof, skill2_name, skill2_prof,
  skill3_name, skill3_prof, cert1_name, cert1_exp, cert2_name, cert2_exp, ...

Problems:
  ✗ Fixed number of skills per employee (not scalable)
  ✗ Massive repeated data (employee name in every row)
  ✗ Hard to query ("skill1_prof is null" not clear)
  ✗ Difficult to validate (skill names scattered across columns)
  ✗ Not extensible (new skill means new columns)

Why Separate is Better:
  The normalized approach trades slight complexity in joining for massive
  gains in data quality, queryability, and maintainability.
